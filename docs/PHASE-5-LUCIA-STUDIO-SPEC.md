# Lucia OS — Phase 5: New Lucia Studio Specification

> **Document ID:** LUCIA-PHASE-5-STUDIO-001  
> **Version:** 0.1  
> **Status:** Approved implementation boundary — implementation in progress  
> **Date:** 2026-11-22  
> **Branch:** `development`  
> **Depends on:** Phase 1 architecture, Phase 2 Graph Engine, Phase 3 Design Intelligence, Phase 4 Composition & Rendering

## 1. Purpose

Build the new customer-facing Lucia Studio as a graph-native authoring workspace. The Studio is a new interface, not an extension or redesign of the legacy editor component tree.

The website graph remains the single canonical representation of website structure and content. The Studio visualizes and edits that graph, displays a contextual inspector, renders an interactive preview from the Phase 4 renderer, navigates validation findings to their exact graph nodes, and exposes immutable revision history.

This phase builds the new Studio alongside the existing editor route. It does not cut over customers or retire the legacy editor; that is reserved for the approved migration and replacement phase.

## 2. Current verified foundation

### Available and reusable

- Graph Engine contracts, validation, transactional mutation service, immutable version snapshots and operation log.
- Tenant-scoped graph read/create/mutation API routes.
- Per-user canvas position persistence, separate from graph content revisions.
- Graph version listing and restore through the `RESTORE_VERSION` graph operation.
- Phase 4 deterministic composition and server-renderable website output.
- Typed renderer diagnostics, responsive HTML, exact token resolution and secure media/shared-data resolver boundaries.
- Existing workspace tab continuity, dirty-state protection and organization permission checks.

### Missing for the new Studio

- A new `/studio` route and Studio-owned component tree.
- Deterministic automatic canvas layout and visual graph presentation.
- Contextual node inspector and safe, typed editing forms.
- A server-authorized preview endpoint and interactive preview navigation adapter.
- A Studio validation aggregation/navigation experience.
- Revision history, restore controls and explicit conflict/recovery UX for Studio workflows.
- Workspace route continuity registration and a new entry from the website picker.

The existing `/editor` route, legacy editor components, draft APIs, public-site rendering and published websites remain unchanged in this phase.

## 3. Product and architecture invariants

1. The Phase 2 GraphDocument is the only source of truth for website structure and content.
2. Canvas coordinates are presentation state only. Moving or arranging nodes must never mutate graph nodes, graph edges, website layout properties or published output.
3. Canvas positions remain scoped to the current user and graph through the existing canvas-position service.
4. Automatic layout is deterministic for equivalent graph structure and layout settings.
5. Nodes represent actual website objects and typed relationships; no decorative-only graph nodes.
6. The inspector edits only registered, typed properties. No arbitrary JSON, executable code, raw HTML, arbitrary CSS or dynamic component/module selection.
7. Every graph mutation uses the existing transactional API, expected revision and idempotency key.
8. A stale revision is a conflict, not permission to overwrite another editor's changes.
9. Preview HTML is generated by the Phase 4 renderer from the canonical graph. Preview must not use a separate website document model.
10. Preview execution is isolated. Graph content is data, never executable script.
11. Validation findings include stable codes and exact node/edge references where available.
12. Restoring history creates a new graph revision; immutable history is never rewritten.
13. No AI dependency is introduced. AI may be integrated later as an optional adapter without becoming a core authoring dependency.
14. No customer website, live route, published output, production data or legacy editor behavior is cut over or deleted in Phase 5.

## 4. Studio workspace structure

The new route is `/studio?websiteId=<uuid>&organizationId=<uuid>`. The organization ID is context only; every server operation independently verifies the signed-in user, organization permission, website ownership and tenant scope.

The Studio shell contains:

- **Top bar:** website identity, save/sync state, undo/history entry, validation status and preview controls.
- **Node canvas:** primary full-workspace surface with zoom, pan, fit-to-view, auto-organize and node selection.
- **Contextual inspector:** opens for the selected node and provides only the fields/actions supported by its registered node-type editor.
- **Preview surface:** renders the actual graph through the Phase 4 renderer with desktop/tablet/mobile viewport controls and in-preview navigation.
- **Validation panel:** lists structural, recipe, token, content and rendering findings; selecting a finding selects and focuses its graph node.
- **History panel:** lists immutable graph revisions and allows a confirmed restore as a new revision.

The layout must remain responsive. On narrow screens, the canvas remains the primary surface and inspector/preview/validation panels become explicit sheets or tabs rather than compressed multi-column panes.

## 5. Node canvas

### 5.1 Node catalogue and visual identity

The canvas visualizes registered graph node types:

- Website
- Page
- Section
- Component
- Design token
- Shared data
- Interaction
- Responsive configuration
- Media reference

Each node card shows a type label, concise human-readable title, relevant status and validation count. Nodes are connected by real graph edges. Edge labels and visual styles must distinguish containment from reference/configuration relationships.

The first editable vertical slice must support the website root, pages and sections. Other registered node types remain visible and inspectable with safe read-only details until a typed editor is explicitly implemented.

### 5.2 Automatic layout

Implement a pure, deterministic layout function over a validated GraphDocument:

- Website root is the top-level anchor.
- Pages are arranged in stable page order.
- Sections are arranged under their owning page in explicit edge order.
- Nested components follow containment depth.
- Reusable/reference nodes are placed in a deterministic reference lane and connected to their source nodes.
- Stable node IDs break ties.
- Layout never writes to graph properties or content edges.

Existing saved user positions override computed positions for nodes that have saved coordinates. Auto-organize recomputes positions for unlocked nodes; locked nodes retain their coordinates. The operation writes only to the canvas-position endpoint.

### 5.3 Canvas interactions and accessibility

- Pointer drag changes canvas position only and persists on drag completion, not every pointer movement.
- Pan and zoom do not change saved node positions.
- Provide fit-to-view, zoom in/out and reset controls.
- Provide keyboard selection and movement controls for nodes.
- Provide a semantic node outline/list alternative to the spatial canvas.
- Node controls have accessible names, visible focus and clear selected/locked states.
- Respect reduced-motion preferences.
- Canvas bounds and coordinate values remain within the existing server contract.

## 6. Contextual inspector and graph editing

### Initial editable properties

- Website: display name.
- Page: title and local path.
- Section: registered recipe reference where supported, heading, description, structured feature/service items and paired call-to-action label/local destination.
- Relationship/order: supported containment reorder and typed connect/disconnect operations.

The inspector must not expose arbitrary property mutation. Each editor has a Zod schema and explicit field mapping.

### Mutation lifecycle

1. Load graph, versions and current user's canvas positions from the authorized graph endpoint.
2. Keep form edits local until the user applies them or invokes the workspace save action.
3. Validate field values before submitting.
4. Submit a bounded mutation batch with current graph revision and a fresh idempotency key.
5. On success, reload/merge the authoritative graph and advance the known revision.
6. On 409 conflict, preserve the user's local form values, show the latest server revision and require an explicit reload/reapply decision.
7. On permission or validation failure, show an actionable message without discarding local values.
8. Mark the workspace tab dirty while unapplied edits exist; register save/discard behavior with workspace continuity.

Node deletion and relationship removal require explicit confirmation and must respect graph validation. No destructive bulk-delete or website-reset action is introduced.

## 7. Interactive preview

### 7.1 Preview adapter

Add an authenticated, tenant-scoped preview API that:

- Loads the canonical graph through the Graph Engine service.
- Verifies the selected page belongs to the graph.
- Calls the Phase 4 `renderWebsite` function.
- Returns rendered HTML or typed diagnostics.
- Does not persist, publish, deploy or mutate graph content.

The preview request identifies page node ID, normalized route and viewport profile. Preview output must be regenerated after graph content changes.

### 7.2 Isolation and navigation

- Render the HTML in a sandboxed iframe.
- Do not grant script execution, top navigation, popups, downloads or form submission.
- If same-origin access is required for parent-controlled navigation interception, use only the minimum sandbox capability and keep scripts disabled.
- Parent-controlled navigation intercepts only validated local page routes and requests a fresh server-rendered preview for that page.
- Never let preview content navigate the real application shell or an external destination.
- Media/shared-data references that cannot yet be resolved must remain explicit diagnostics; do not substitute unrelated content.

### 7.3 Viewport controls

Provide desktop, tablet and mobile controls. The iframe viewport width changes to the selected profile while the renderer remains the authority for responsive HTML/CSS. Preview viewport selection is not a graph mutation.

## 8. Validation and issue navigation

Aggregate findings from:

- Graph Engine structural/property validation.
- Design Intelligence recipe/version compatibility.
- Required token resolution.
- Composition content requirements and unsupported feature detection.
- Per-page renderer preflight and media/shared-data resolution.

Each finding contains severity, stable code, message, and affected node/edge IDs or request/property context when available.

Selecting a finding must:

1. Select the affected graph node.
2. Move the canvas viewport to that node.
3. Open the relevant inspector section.
4. Highlight the invalid field or relationship when a property path is supplied.

Validation is deterministic and does not call AI or mutate graph content. Findings must distinguish blocking errors from warnings and informational guidance.

## 9. History, undo and recovery

- Display graph versions by revision, author and timestamp.
- Show content hash as technical metadata, not as a user-facing identity.
- Restore uses the existing immutable version ID and the `RESTORE_VERSION` mutation.
- Restore creates a new revision; it never rewrites or deletes history.
- Require confirmation before restore and explain that the current draft will become a new revision.
- On stale revision, reload history and require the user to retry explicitly.
- Canvas position changes do not create graph content history entries.
- Unapplied inspector edits participate in workspace dirty protection and are not silently lost on navigation.

## 10. Security and privacy

- All graph, history and preview operations require a verified session and tenant permission.
- Organization and website IDs from query strings or headers are identifiers, never authorization.
- Use the existing Graph Engine service and RLS boundaries; do not query graph tables directly from client components.
- Do not return private resolver URLs, tenant records or internal secrets to the browser.
- Preview output is sandboxed and contains no arbitrary executable graph content.
- Validate all route, node, revision and mutation inputs.
- Do not introduce a new persistence representation or database migration without a separately verified need.
- Do not modify production routes, publishing, billing, domains or existing customer websites.

## 12. Implementation sequence

1. **Studio foundation:** typed Studio contracts, deterministic graph-to-canvas auto-layout, focused tests and isolated route registration. No legacy editor changes.
2. **Node canvas:** accessible node cards, real graph edges, selection, pan/zoom, auto-organize and persistence through the existing canvas endpoint.
3. **Inspector and editing:** typed website/page/section forms, graph mutation adapter, optimistic concurrency, dirty protection and conflict UX.
4. **Preview:** authenticated preview endpoint, sandboxed iframe, local route navigation and viewport controls.
5. **Validation navigation:** aggregate graph/recipe/token/render diagnostics and exact node/field navigation.
6. **History and recovery:** revision history, restore-as-new-revision and workspace save/discard integration.
7. **Full verification:** focused tests, full unit suite, typecheck, lint, production build, routing/security checks and accessibility-oriented acceptance.

Each increment must be committed to `development` and verified before the next dependent increment. Do not remove or replace the legacy editor route in Phase 5.

## 13. Acceptance criteria

- A new Lucia Studio route exists independently of `/editor`.
- The canvas visualizes actual graph nodes and typed edges.
- Automatic layout is deterministic and respects saved/locked canvas positions.
- Dragging, zooming and auto-organizing never change graph content or published website layout.
- Canvas positions are persisted through the existing user-scoped canvas service.
- Website, page and section inspectors edit only registered properties through Graph Engine mutation APIs.
- Optimistic revision conflicts preserve local user edits and require explicit resolution.
- Preview is generated by the Phase 4 renderer, navigable between actual graph pages and isolated from script execution.
- Desktop/tablet/mobile preview controls work without graph mutation.
- Validation findings navigate to the exact graph node and relevant field where available.
- History restore creates a new immutable graph revision.
- Workspace dirty/save/discard behavior protects unapplied edits.
- All server operations enforce tenant authorization; no client-side role or organization claim grants access.
- Accessibility, security, responsive and regression tests pass on the exact final Phase 5 implementation commit.
- No production data, existing websites, published output, legacy editor route, billing, domains or live infrastructure is modified or deleted.
